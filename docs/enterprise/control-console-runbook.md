# Enterprise Control API and console

The Spring Boot API under `java/enterprise-control-api` exposes governed tenant, organization, project, integration, quota, cost and API-key lifecycle intents. It does not mutate those business tables. Each write recomputes the canonical request binding, signs the verified human principal, and submits the intent to the mTLS Enterprise Authority. That authority emits Canonical Action IR into the durable orchestrator; PEP, execution ledger, Tool Proxy and signed Evidence remain the execution authority. HTTP `202` means the action was durably accepted and start was requested, not that the mutation or task completed. API-key material is created only by the governed executor, stored in Vault, and represented to callers by a non-secret credential reference; the browser and BFF never receive raw key material.

The BFF aggregates authoritative service ports with bounded connection/read timeouts; it never joins service databases or manufactures a complete response when a dependency fails. Every query is tenant scoped and bounded. Admin actions require an OAuth2 JWT subject, tenant/project scope, RBAC/ABAC, secure double-submit CSRF and separated approval.

The dashboard contract contains exactly 21 sections. In addition to the core task, identity,
approval, policy, incident, audit and deployment views, the production runtime sections are
`MODELS`, `DATA`, `CONTEXT`, `ANOMALIES`, `SECURITY_EVALUATIONS`, `SUPPLY_CHAIN`,
`DOMAIN_PACKS`, and `SRE`. Each has one explicit collection route, one distinct read token,
an exact readiness schema, tenant header/query binding, and a bounded cursor. These pages set
`authoritative=true` and carry a JCS SHA-256 over the complete response after removing only
`data_digest`; the BFF recomputes that digest with a constant-time comparison. It also rejects
unknown fields, missing sections, disagreement between availability and `unavailable_sections`,
raw prompt/content/credential fields, non-integral numbers, excessive depth or size, and any
unavailable section that does not use a null payload plus the zero digest. The browser repeats the
complete-section and partial-failure checks and never receives a service credential.

Production startup requires the explicit IAM issuer, authorization, token, user-info and JWKS endpoints; the PEP and every authority HTTPS endpoint plus its exact readiness schema; outbound mTLS key/trust stores; database credentials and expected role; AG-UI signing material; and the human-principal signing configuration. The API-key pepper belongs only to the Enterprise Authority executor and is never mounted into the BFF. There is no global `AGENT_TRUST_SERVICE_TOKEN`. Every authority read or operation scope has its own absolute secret file and startup rejects duplicate paths or duplicate raw token values. In particular, Enterprise writes use `AGENT_TRUST_ENTERPRISE_AUTHORITY_ENDPOINT`, `AGENT_TRUST_ENTERPRISE_AUTHORITY_READINESS_SCHEMA`, and `AGENT_TRUST_ENTERPRISE_MUTATE_TOKEN_FILE`. Policy reads use `AGENT_TRUST_POLICY_ADMIN_READ_TOKEN_FILE`; all twelve lifecycle mutations use the distinct `AGENT_TRUST_POLICY_MUTATE_TOKEN_FILE` and `policy:mutate` scope. PEP approval/query and the five Approval scopes use separate tokens. The rendered production stack is the authoritative inventory of the full environment-variable and CSI/Vault contract.

The BFF database account must be `NOSUPERUSER NOBYPASSRLS`; its connection uses `sslmode=verify-full`, an explicit CA, and the exact `pg_catalog,public` search path. Its least-privilege grants cover only remote-action state, approval-intent state, and the application-private Spring Session tables. It has no write privilege on the enterprise business tables, API keys, legacy idempotency table, or admin-action table. Each tenant transaction sets `app.tenant_id` locally. Spring Session tables are application-global opaque storage and must never be shared with another application or cookie namespace; tenant authority is reconstructed from the verified principal on every request.

The Vue console displays unavailable sections explicitly, sends intents only, and strictly validates the versioned Agent inventory, approval, task and policy response shapes. The eight production runtime views are first-class navigable modules backed only by their BFF authority sections; they do not call Rust services directly. Policy Studio reads the keyset-paginated `/policies` collection plus bounded sources, analyses, reviews, simulations, impact reports, promotions and exceptions. It submits only `POST /policies/actions`; the removed direct simulation and promotion POST routes must never be restored. The BFF binds the exact body, tenant, mTLS SAN, service subject, scope and idempotency key into a strong-auth Ed25519 assertion, then accepts only the exact Policy receipt with `execution_pending=true`. The UI computes and checks canonical source, simulation, impact and promotion digests with Web Crypto, shows SoD and exception compensation/expiry facts, and never converts HTTP `202` into lifecycle success. Production builds fail when the Control API or AG-UI verification key is missing or unsafe, and public source maps are disabled. Task completion is shown only when runtime state, ledger, evaluator, and Evidence agree.

Before production, connect enterprise IAM, provision tenant/organization/project ownership, run authenticated browser E2E including cross-tenant, IDOR, CSRF/XSS and sensitive-export negatives, exercise partial BFF failure, and validate live IAM/notification/ticketing/SIEM/Webhook adapters. These external gates remain `NOT_RUN`.
